Why Your RAG Pipeline Answers Confidently and Retrieves Wrong

Jacklyn Miller

Most RAG debugging conversations start the same way: the retrieval pipeline seems correct on paper, the LLM is generating fluent responses, but the answers are subtly wrong. Not hallucinated — just off. They sound like they came from your documents, sort of.

This is the part of RAG that observability tools were built for. The failure isn't in the model. It's in what the model doesn't see.

This post walks through the most common retrieval failures, why they're hard to catch without visibility into the pipeline, and what it looks like to fix them.

The Retrieval Gap: What It Is and Why It Compounds

When a user submits a query, your retrieval system computes a similarity score between that query's embedding and the embeddings in your vector store. The top-k chunks get passed to the LLM as context. The LLM generates an answer from whatever it received.

The problem is that the LLM has no way to signal that the context it received was insufficient or exceeds the context window. It will produce a coherent answer from low-relevance chunks the same way it produces a coherent answer from high-relevance ones, in the exact same voice and tone. Confidence of output is misleading and tells you almost nothing about quality of retrieval.

This means retrieval failures are invisible at the generation layer. You need to look upstream.

Four Retrieval Failures Worth Knowing

Failure 01

Chunk boundary fragmentation

Retrieval operates on chunks, not documents. If your chunking strategy cuts a concept in half — for example, a question answered across two chunks with no overlap — neither chunk alone will score high enough to surface in the top-k, even though the answer exists in your knowledge base.

Example: A user asks about ADDIE's Evaluation phase. Your document covers ADDIE in a single section that runs 1,400 tokens. With a 1,000-token chunk size and no overlap, the Evaluation phase lands in chunk 2. Chunk 1 scores higher for the word "ADDIE" and gets retrieved. The answer is incomplete.

Fix: Increase chunk overlap (200–300 tokens is a reasonable starting point for narrative content) and experiment with semantic chunking strategies that try to split on topic boundaries rather than token counts.

Failure 02

Embedding mismatch between query and document language

Embeddings encode semantic similarity, but that similarity is trained on patterns in the embedding model's training data. If your users ask questions in different language than your documents use, retrieval degrades.

Example: Your knowledge base uses smart, formal academic language: "Andragogical principles suggest learners are self-directed." A user asks: "How do adults learn best?" The semantic distance between these phrasings may be larger than you expect, especially for domain-specific vocabulary.

Fix: Evaluate your embedding model on representative query/document pairs from your actual domain. Consider query rewriting — using the LLM to rephrase the user's query in document-style language before retrieval — as a preprocessing step.

Failure 03

Top-k set too small for complex questions

Simple factual questions often need only one or two chunks. Multi-part questions, comparative questions, or anything requiring synthesis across concepts need more. A fixed top-k setting that works for simple queries will silently fail on complex ones.

Example: "Compare constructivism and behaviorism for corporate training contexts" may require chunks from three or four separate document sections. A top-k of 3 might return three constructivism chunks and miss behaviorism entirely.

Fix: Implement dynamic top-k selection based on query complexity, or use a re-ranking step that scores chunks for relevance after initial retrieval and expands the context window for queries that need it.

Failure 04

Vector store staleness

If your knowledge base updates but your vector store doesn't re-embed, you're retrieving from an outdated index. This is especially common in applications where the knowledge base is a living document — product documentation, policy guides, internal wikis.

Fix: Implement a document hash check on load. If the source document has changed since the last embedding, trigger a re-embed for that document. Avoid full re-indexing on every launch — it's expensive and unnecessary.

What This Looks Like in a Real Pipeline

Here's a simplified version of a retrieval chain setup that makes some of these failure modes more visible:

# Enable verbose output to see what chunks are being retrieved
chain = ConversationalRetrievalChain.from_llm(
    llm=llm,
    retriever=vectorstore.as_retriever(
        search_kwargs={'k': 5}  # start higher than you think you need
    ),
    return_source_documents=True,  # critical for observability
    verbose=True,
    callbacks=[StdOutCallbackHandler()]
)

Setting return_source_documents=True is the minimum viable observability step. It lets you inspect what the retriever actually returned and compare it against what the LLM used in its answer. Without this, you're debugging blind.

For production pipelines, you want to log retrieved chunks alongside queries and responses so you can identify patterns: which queries consistently return low-relevance chunks, which document sections are never retrieved despite containing relevant content, where the LLM's answer diverges from what the sources actually say.

This is exactly the kind of signal that makes evaluation frameworks useful. Logging retrieval isn't just for debugging — it's the feedback loop that lets you continuously improve chunk strategy, embedding choice, and top-k configuration over time.

A Note on Evaluation

Retrieval quality is hard to evaluate without ground truth — pairs of queries and the chunks that should have been retrieved for them. Building even a small evaluation set (20–30 representative queries with expected source documents) gives you something concrete to measure against when you change chunking strategy or swap embedding models.

Without it, you're measuring retrieval quality by proxy (does the LLM answer sound right?) which is unreliable for the reasons covered above.

Summary

  • Retrieval failures are invisible at the generation layer — you need to observe the pipeline upstream of the LLM
  • Chunk boundary fragmentation, embedding mismatch, insufficient top-k, and vector store staleness are the four most common failure patterns
  • return_source_documents=True and verbose logging are the minimum instrumentation you need to start diagnosing retrieval quality
  • A small ground-truth evaluation set is the difference between iterating on intuition and iterating on evidence
